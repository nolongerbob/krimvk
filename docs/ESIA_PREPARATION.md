# Подготовка ЕСИА (22.09.2026)

Статус: изолированный UX-макет, НЕ рабочий провайдер авторизации.

## Что можно проверить сейчас

Изолированный запуск без БД и внешних интеграций: `node scripts/dev-seasonal.mjs --esia-preview`.
Макет: `http://localhost:3006/dev/esia`. Отдельная папка сборки `.next-esia-dev`,
поэтому основной dev на порту 3005 можно оставить работающим.

При запуске локального `next dev` задать серверную переменную
`ESIA_DEV_PREVIEW=true`, открыть `/dev/esia`. По умолчанию маршрут закрыт.
В production он возвращает 404 даже с этим флагом. На `/login` под обычным
входом добавлена кнопка, видимая только при dev opt-in. Нажатие показывает
явно обозначенный пример конфликта: войти по паролю и привязать Госуслуги
в настройках. В `/dashboard/settings` добавлен dev-блок явной привязки,
также без реальной операции. Регистрация не меняется. Макет не отправляет запросы в ЕСИА, не получает
персональные данные, не пишет в БД и не выдаёт сессии.

Старая неподтверждённая заготовка generic OAuth удалена из auth-config:
`GOSUSLUGI_CLIENT_ID` и `GOSUSLUGI_CLIENT_SECRET` больше не включают провайдер.
Автоматическая привязка по email удалена. Авторизация credentials сохранена.

## Контракт будущей реализации (не считать реализованным)

- Выбрать допущенное типовое решение либо согласовать собственное решение.
- Уточнить транспорт, требования СКЗИ, сертификат ИС и разрешённые scopes.
- Разделять идентичности тестовой и промышленной ЕСИА; тестовые субъекты
  не могут получить production-сессию.
- Начало входа: одноразовая серверная транзакция с коротким TTL, state,
  ожидаемым окружением, назначением (login/link) и локальным return URL.
- Callback: проверить state, срок и одноразовость, подпись/issuer/audience,
  сроки токенов и привязку ответа к запросу по актуальному контракту адаптера.
  Не доверять query-параметрам с пользовательским идентификатором.
- Маппинг только по проверенному идентификатору ЕСИА + окружению. Никогда
  не искать владельца для автоматической привязки по ФИО/email/СНИЛС.
- Привязка: подтверждённая локальная сессия с недавней повторной проверкой,
  явное согласие пользователя, уникальность связи и транзакция в БД.
- Новый пользователь: отдельный сценарий регистрации и подтверждение нужных
  контактов; не создавать фиктивную почту при отсутствии email в ЕСИА.
- Отвязка не должна удалять последний доступный способ входа.
- Роли брать из локальной БД; вход через ЕСИА не повышает роль и не даёт
  права на лицевой счёт. Существующие счета/платежи/обращения сохраняются.
- Не отдавать токены провайдера в браузер, не писать их в логи. Запрашивать
  минимальные данные, не хранить refresh token без обоснованной потребности.

## Внешние зависимости и порядок

Регламент ЕСИА 2.54: таблица 1 (стр.18), раздел 6 (стр.32), раздел 9
(стр.42–53), раздел 10 (стр.54–67), Приложение Г (стр.98–101).
Карточка в промышленном техпортале -> заявка на тест -> тестирование ->
отдельное согласование промышленного подключения. Нужны организация,
ответственный сотрудник, основание подключения и техническое решение.
Плановая мнемоника `KRYMVK_LK` ещё не зарегистрирована.
URL callback не подавать в заявку до выбора/проверки адаптера.

## Условия включения

Сначала тестовый адаптер и тестовая БД, затем тесты отмены, просрочки,
подмены state, повторного callback, неверной подписи, конфликтов привязки,
параллельных запросов, смены сессии и изоляции окружений. Прогнать регрессию
обычного входа/сброса пароля. Только после допуска и отдельного разрешения
добавить production-провайдер и публичную кнопку. Переменной-флага для
включения настоящей ЕСИА в текущей версии намеренно нет.
