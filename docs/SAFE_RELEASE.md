## Подготовка

1. Сформировать проверенный commit: незакоммиченные dev-изменения в архив не попадут. Проверить сохранение hotfix `be4e74b`.
2. Настроить переменные `RELEASE_REF` (commit), `RELEASES_DIR` (отдельный каталог вне активного checkout), `RELEASE_ENV_FILE` (существующий production env вне releases), `METER_SUBMISSION_DIR` (существующий журнал).
3. Запустить новую копию скрипта от пользователя приложения через `bash scripts/deploy-vps.sh --prepare`. Создаётся уникальный каталог с собственными зависимостями и сборкой. При ошибке каталог остаётся для диагностики, активный процесс не затрагивается.
4. GitHub workflow запускается только вручную, получает скрипт из выбранного commit и делает только подготовку. Environment variables GitHub: `RELEASES_DIR`, `RELEASE_ENV_FILE`, `METER_SUBMISSION_DIR`. Секреты SSH/путей остаются в GitHub Secrets. Push сам ничего не выкладывает.

## Миграции — отдельный согласованный шаг

Скрипт запускает `prisma migrate status` без изменения схемы и останавливается при pending/failed миграциях. Не отмечать миграции выполненными без сверки реальной схемы. Перед применением нужны резервная копия и проверка восстановления.

В проверке от 21.09 ожидались `20250605120000_add_performance_indexes` и `20260921110000_site_notices`; 28.09 добавлена `20260928120000_utility_account_recovery`. Актуальное состояние целевой базы требуется проверить заново. CREATE INDEX без CONCURRENTLY может блокировать запись: проверить размеры таблиц и длительность на staging, выделить окно. Применять `prisma migrate deploy` из нового релиза с тем же production окружением после отдельного разрешения. Prisma CLI нужно загрузить `.env.production.local` через `@next/env`, как в скрипте. Никакого fallback на `db push`. После применения повторить подготовку/проверки.

## Переключение — не автоматизировано этим скриптом

После отдельного разрешения:

1. Запустить новый процесс из подготовленного каталога на свободном порту, только `127.0.0.1`, с production окружением, прежним журналом и `HEALTHCHECK_DB=1`. Не перезапускать старый `krimvk`.
2. Проверить `/api/health` (реальная БД), авторизацию, документы, переписку; не отправлять выдуманные показания в рабочую 1С. Сверить окружение PM2: файл `.env.production.local` и явно переданный журнал должны использоваться и при перезапуске.
3. До переключения решить раздачу старых `/_next/static` файлов для уже открытых страниц: сохранить оба набора ассетов. Не удалять старую сборку.
4. Сохранить текущую конфигурацию Nginx, изменить только upstream, выполнить `nginx -t`, затем graceful reload. Для этого нужны права администратора. Проверить публичный сайт, а не только health нового порта.
5. Если проверка не проходит — вернуть прежний upstream, `nginx -t`, reload. Старый процесс, код и зависимости остаются нетронутыми. Миграции БД автоматически не откатывать; они должны быть совместимы с обеими версиями.
6. Только после успешной проверки согласовать завершение старого процесса и PM2 save. Не удалять журнал и не очищать releases в рамках переключения.

Новые возможности управляются флагами сборки и общими настройками администратора; см. DEV_RELEASE_GATE.md и .env.example.vps. Капелька и осень по умолчанию выключены, локальная dev-настройка браузера в production не используется.
