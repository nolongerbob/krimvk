# Пароли и почта лицевого счёта 1С

## Что реализовано

- Смена пароля и синхронизация почты — только база `saki` (существующий пункт районов «Сакский и Симферопольский»). Остальные коды блокируются и в UI, и на сервере для этих новых методов.
- В административном чате рядом с ИИ-ответами — «Пароль 1С». Номер ЛС вводится вручную. Генерация восьми символов или собственный пароль, установка в 1С, проверка через `GetAccountPassword`, отправка в выбранный диалог.
- Если ЛС уже привязан к другому пользователю/району, операция блокируется. Для непривязанного ЛС оператор сам проверяет личность получателя до отправки.
- Подтверждённый email профиля переносится в 1С после привязки ЛС, подтверждения/смены email и успешной смены пароля оператором. В окне оператора есть отдельная повторная синхронизация почты.
- «Забыли пароль лицевого счёта?» в добавлении ЛС отправляет ссылку на подтверждённую почту ЛК. Пароль сайта не меняется.

## Добавление счёта оператором

Открыть профиль пользователя из чата или списка пользователей → «Лицевые счета» (либо «Настройки») → «Добавить лицевой счёт». Указать район, номер и действующий пароль 1С. В форме явно указан получатель; счёт добавляется ему, а не оператору.

Привязка поддерживает все существующие районы, использует свежий `get_data` без кеша и не меняет пароль 1С. Счёт и счётчики создаются одной транзакцией. Существующая чужая привязка, дубликат и смена пароля во время проверки блокируют добавление. Для `saki` после привязки отдельно синхронизируется подтверждённая почта получателя; её недоступность не отменяет успешное добавление. В режиме `ONE_C_READ_ONLY=true` привязка на сайте работает, запись почты в 1С пропускается с предупреждением.

Новый API: `POST /api/admin/users/[id]/accounts`, только ADMIN, проверка Origin, ограничение частоты, повторная проверка роли и получателя в транзакции. Секрет не возвращается в API и хранится зашифрованным; `PASSWORD1C_ENCRYPTION_KEY` обязателен и в dev.

## Ограничение восстановления

Текущий `get_data` не возвращает email, а среди новых методов нет чтения email. Поэтому нельзя безопасно восстановить любой неизвестный сайту ЛС по номеру и произвольной почте.

Восстановление разрешено только при сохранённой связи `пользователь → ЛС → подтверждённый email`, после успешного `UpdateAccountEmail`. Эта запись сохраняется при отвязке ЛС, поэтому его можно добавить заново после восстановления. Старые/ещё не привязанные счета без такой связи восстанавливаются оператором. Для самостоятельного первичного восстановления старых счетов потребуется доверенный метод чтения email из 1С или иной способ проверки владельца.

## HTTP-контракт

Используется существующий транспорт WebAccounts: GET `/{region}/hs/WebAccounts/{method}`, без кеширования и редиректов.

- `UpdateAccountEmail`: `WaLsCode`, `WaNewEMail`.
- `ResetAccountPassword`: `WaLsCode`, `WaNewPass`.
- `GetAccountPassword`: `WaLsCode`; JSON-объект с `WaLsPass`.

Мутации ожидают HTTP 2xx с пустым телом или JSON без ошибки. После сброса пароль обязательно сверяется чтением, включая случай потерянного ответа записи. Форматы успешных ответов новых методов следует подтвердить на согласованном тестовом ЛС перед включением в production.

## Безопасность и эксплуатация

- `ONE_C_READ_ONLY=true` запрещает реальные записи. Текущий локальный запуск `dev-seasonal.mjs` оставляет этот режим включённым и не подключает почтовый сервис. Автоматические проверки используют локальный HTTP-стенд вместо настоящей 1С; реальные пароли не меняются.
- Для включения нужны применённая миграция `20260928120000_utility_account_recovery`, Prisma Client, настроенные `PASSWORD1C_ENCRYPTION_KEY`, `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, корректный HTTPS-адрес сайта; запись в 1С должна быть разрешена. В production дополнительно обязателен `ONE_C_UTILITY_ACCESS_ENABLED=true` и HTTPS в `ONE_C_API_BASE_URL`. Флаг включать только после проверки ACL/аутентификации сервиса и его ответов на согласованном тестовом ЛС. Не следует отключать read-only у локального стенда только ради визуальной проверки.
- До включения флага сервер блокирует все три новых метода, в том числе чтение пароля для сверки. HTTP разрешён только на loopback-стенде вне production. Обычные чтение баланса/показаний и передача показаний не зависят от нового флага. UI оператора использует ту же проверку готовности, что и сервер, а не только наличие ключа шифрования.
- Новые методы 1С должны быть закрыты от публичного доступа сетевым ACL/VPN/аутентификацией. Они принимают один номер ЛС и позволяют читать/менять пароль; защита Next.js не защищает прямое обращение к 1С. Используйте защищённый канал и отключите журналирование query string этих методов. Публичный HTTP без ограничения доступа не годится для боевого включения.
- `GetAccountPassword` доступен только внутреннему серверному коду, API для показа существующего пароля нет. Исключения/логи не содержат URL 1С, пароли и её тела ответов.
- Изменение пароля имеет постоянный идентификатор операции, сериализацию по ЛС и журнал. Повтор не вызывает второй Reset. Неопределённый результат удерживает блокировку до сверки; оператор нажимает «Проверить результат» в том же окне. Перезагрузка сохраняет только идентификатор операции, не пароль. Не удаляйте PENDING-журнал вручную без сверки состояния 1С.
- Пароль в журнале незавершённой операции зашифрован и очищается после завершения. В сообщении он сохраняется как часть приватного чата по требованию продукта. Сообщение помечено `isSensitive` и исключено из серверных выборок контекста ИИ, примеров ответов и базы знаний.
- Ссылка восстановления: 256 бит случайности, в БД только SHA-256, срок 15 минут, одноразовое использование, привязка к пользователю/ЛС/почте. GET и открытие письма пароль не меняют. Повтор после неопределённого результата только сверяет ранее начатую операцию.
- Добавление ЛС всегда заново проверяет пароль в 1С, не принимает старый кеш как доказательство входа.

## Проверки

Обычные unit/API/UI-тесты: `jest --runInBand` с файлами `1c-account-access`, `utility-password-change`, `utility-email-recovery`, `utility-access`, `utility-password-ui`.

Интеграционный прогон только для изолированной локальной БД:
`UTILITY_LOCAL_DB_TEST=1 jest --runInBand __tests__/lib/utility-access-local.integration.test.ts`.
Он создаёт собственные синтетические записи, поднимает ложный HTTP-сервис на 127.0.0.1, проверяет полный цикл и удаляет только созданные им записи. Почта замокана, обращений к реальной 1С нет.
